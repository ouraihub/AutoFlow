## 3. 阶段推进：`src/core/stage.ts`

### 3.1 事件来源

阶段只从 issue 评论算出来，评论是只追加的事件日志。分支上的文档只决定提示词内容和结论，不参与推进。这样 Worker 的 `/status` 和 prepare 用同一个函数，结果一致。

| 事件     | 认定条件                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 运行报告 | 作者是 GitHub Actions 机器人，首行匹配 `^AutoFlow agent: ([a-z-]+) ([a-z-]+)\.$`，并且阶段和结论都是 §3.2 里的值。其他人写的同样文字、不认识的阶段或结论一律忽略，防止伪造结论 |
| 你的评论 | `authorAssociation` 为 `OWNER`，和现在工作流的触发条件一致。正文先过 `ownText`                                                                                                 |

机器人登录名：REST 里是 `github-actions[bot]`，`gh issue view` 里可能显示为 `github-actions`。第一次真实运行时把两处实际值写进测试，不要猜。

### 3.2 类型

```ts
export type RunStage =
  | 'requirements'
  | 'test-cases'
  | 'architecture'
  | 'architecture-review'
  | 'design'
  | 'design-review'
  | 'develop'
  | 'acceptance'
export type Stage = RunStage | 'await-requirements' | 'await-design' | 'await-decision' | 'review-pr'
export type Outcome = 'done' | 'changed' | 'unchanged' | 'pass' | 'reject' | 'reject-architecture' | 'paused' | 'failed'
export type FlowEvent = { kind: 'report'; stage: RunStage; outcome: Outcome } | { kind: 'owner'; text: string }
export type FlowState = {
  stage: Stage
  /** 下一步要等你的评论：所有 await-*、review-pr，以及运行阶段 paused / failed 之后。只有 waiting 时你的评论才会派发运行。 */
  waiting: boolean
  /** 当前这一轮评审或验收计数，用于 /status 和轮次上限。 */
  round: number
  /** await-decision 时被卡住的评审阶段。 */
  blocked: 'architecture-review' | 'design-review' | 'acceptance' | null
}
export function nextStage(events: readonly FlowEvent[]): FlowState
export function formatReport(stage: RunStage, outcome: Outcome): string // 报告首行
```

`nextStage` 从 `{ stage: 'requirements', waiting: false }` 开始逐条折叠。issue 已关闭时 Worker 直接显示"已完成"，不调用它。

### 3.3 转移表

| 当前                 | 事件                                                  | 下一个                                                                             |
| -------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 任意运行阶段 X       | 报告 `X paused` / `X failed`                          | X，waiting                                                                         |
| X，waiting（暂停后） | 你的任意评论                                          | X，继续                                                                            |
| requirements         | `done`                                                | await-requirements                                                                 |
| await-requirements   | 确认 / 其他文字                                       | test-cases / requirements                                                          |
| test-cases           | `done`                                                | architecture                                                                       |
| architecture         | `changed` / `unchanged`                               | architecture-review / design                                                       |
| architecture-review  | `pass` / `reject`                                     | design / architecture                                                              |
| design               | `done`                                                | design-review                                                                      |
| design-review        | `pass` / `reject` / `reject-architecture`             | await-design / design / architecture                                               |
| await-design         | 确认 / 其他文字                                       | develop / design，详细评审重新计数                                                 |
| develop              | `done`（任务全勾且 omp 正常退出）                     | acceptance                                                                         |
| acceptance           | `pass`（publish 同一次开 PR 或更新已有 PR）/ `reject` | review-pr / develop                                                                |
| review-pr            | 你的任意评论（例如按审查意见改）                      | develop，验收重新计数                                                              |
| 评审或验收 `reject`  | 这一类已经连续 2 轮不通过（优先于上面的 reject 行）   | await-decision，`blocked` 为该阶段                                                 |
| await-decision       | 确认 / 其他文字                                       | 按"通过"继续 / 回到被打回的那一步（architecture、design 或 develop），该类重新计数 |

- 轮次分三类单独计数：概要评审、详细评审、验收。`reject-architecture` 计入详细评审。
- 运行阶段中、没有 waiting 时收到你的评论：阶段不变，也不派发（§6.1）。评论会进入后面运行的提示词。
- 报告的阶段和当前阶段对不上（例如重复派发后旧运行晚到）：忽略这条报告。`nextStage` 是纯函数，不记日志。
- 测试覆盖 02 §15 第 1 步列的全部情况，另加：伪造的报告被忽略；连续打回到上限；`await-decision` 的两种回复；在 `review-pr` 回复后重走验收。

## 4. 角色：`src/agent/roles.ts`

每个运行阶段一条配置，prepare 和 publish 都只查这张表：

```ts
export type Role = {
  stage: RunStage
  /** 允许改的路径前缀（相对仓库根）；null = 代码阶段，除了 readOnly 和 protected_paths 都能改。 */
  writes: ((paths: Paths) => readonly string[]) | null
  /** writes 为 null 时不能改的路径前缀，见 02 §4 末段。 */
  readOnly: (paths: Paths) => readonly string[]
  skills: readonly ('ponytail' | 'hallmark' | 'shadcn-svelte')[]
  /** 提示词里这个角色的规则，见 §4.2。 */
  rules: readonly string[]
}
export type Paths = { issueDir: string; architecture: string; standards: string } // docs/issue-N、architecture_path、standards_path
```

### 4.1 可写路径

| 阶段                | 可写                                                      |
| ------------------- | --------------------------------------------------------- |
| requirements        | `<issueDir>/需求.md`                                      |
| test-cases          | `<issueDir>/测试用例.md`                                  |
| architecture        | `<architecture>`、`<standards>`、`<issueDir>/详细设计.md` |
| architecture-review | `<issueDir>/评审.md`                                      |
| design              | `<issueDir>/详细设计.md`                                  |
| design-review       | `<issueDir>/评审.md`                                      |
| develop             | 任意，除了 readOnly 和 `protected_paths`                  |
| acceptance          | `tests/acceptance/<issue-N>/`、`<issueDir>/测试报告.md`   |

develop 的 readOnly：`需求.md`、`测试用例.md`、`评审.md`、`测试报告.md`、`tests/acceptance/<issue-N>/`、`<architecture>`、`<standards>`。`详细设计.md` 可改（勾选任务、写进度）。

越界处理沿用现在设计阶段的做法：只保留允许的文件，单独提交，回帖列出丢弃的文件。develop 越界则整次不推送，和现在一样。

### 4.2 提示词

`prompt.ts` 的结构不变：通用规则、角色规则、需要读的文档、issue 正文（视为数据）、你的评论。变化：

- 通用规则开头加一句：先读 `<standards>`（存在时）和 `AGENTS.md`，规范要求的必须做到，规范和需求都没要求的不加。这句放在 skill 之前。
- 每个角色只把 02 §4 "读"那一列的文件路径写进提示词，让 omp 自己读，不把正文塞进提示词。验收阶段不提设计文档和 `评审.md`。
- 角色规则写明产物格式：`需求.md` 的 R 编号、`测试用例.md` 标注 R 编号、`评审.md` 和 `测试报告.md` 的固定行（见 02 §17.2）。
- 被打回后再运行（design、architecture、develop），提示词指向 `评审.md` 或 `测试报告.md` 最后一节，要求逐条回应。
- 每个角色都保留"写完一节就提交"和最终总结的规则。

### 4.3 skills

按 02 §10 的表，另按项目判断：

- shadcn-svelte：仓库根 `package.json` 依赖里有 `svelte`，或者 `<architecture>` 里出现 `shadcn-svelte`。
- hallmark：仓库里有 `.svelte`、`.tsx`、`.vue`、`.html` 文件（用 `git ls-files` 判断），或者 `需求.md` 里出现"界面""页面""UI"。

判断写成纯函数 `enabledSkills(role, facts)`，`facts` 由 prepare 收集，便于测试。

## 5. 模型：`src/agent/relay.ts`、`omp-config.ts`

```ts
export type RelayModel = {
  id: string
  protocol: 'openai-chat' | 'openai-responses' | 'anthropic-messages'
  model_type: 'chat' | 'image'
}
export type RelayGrant = { key: string; expiresAt: number; models: readonly RelayModel[] }
export async function exchange(relayUrl: string, oidcToken: string, fetcher: typeof fetch): Promise<RelayGrant>
export function ompSetup(input: { relayUrl: string; model: RelayModel; skills: SkillDirs }): OmpSetup
```

- OIDC 令牌在 prepare 里用 `ACTIONS_ID_TOKEN_REQUEST_URL` 加 `&audience=<relay_url 的 origin>`、`Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN` 申请。
- `exchange` 对返回体逐项收窄（`guard.ts`），不对就抛 `upstream`。401、403、503 抛 `config`，`context.status` 带上状态码，publish 据此写提示（02 §17.3）。
- 输入 `model` 在 `models` 里找 `model_type: 'chat'` 的同名项，找不到抛 `config`，消息里列出可用 id，不自动换别的模型。
- `models.yml`：一个 provider `relay`，`baseUrl: <relay_url>/relay/v1`，`apiKey` 指向环境变量 `AUTOFLOW_RELAY_KEY`，`authHeader: true`。每个模型单独写 `api`，按 protocol 映射：

  | 转发 protocol        | omp `api`            | omp 实际请求（baseUrl 为 `…/relay/v1`） |
  | -------------------- | -------------------- | --------------------------------------- |
  | `openai-chat`        | `openai-completions` | `POST /relay/v1/chat/completions`       |
  | `openai-responses`   | `openai-responses`   | `POST /relay/v1/responses`              |
  | `anthropic-messages` | `anthropic-messages` | `POST /relay/v1/messages?beta=true`     |

  2026-10-26 用 omp 18.12.3 对本机回环服务实测，三种都带 `Authorization: Bearer`、不带 `x-api-key`，和 AutoNote 转发的路由、鉴权一致。不认识的 protocol 抛 `config`。把这张表写成 `omp-config.test.ts` 的用例。

- `config.yml`：不写 `retry.fallbackChains`；写 skills（§6.2 第 4 步）。
- key 先 `::add-mask::`，再写进 `GITHUB_ENV`，和现在的做法一样。

### 5.1 并发和有效期

由 AutoNote 转发负责，设计见 AutoNote `docs/43-模型转发设计及开发规划.md` §12：GitHub 临时密钥同时 32 个请求、超出返回带 `Retry-After` 的 429（omp 会等待后自动重试），有效期 6 小时（等于 GitHub 托管 runner 单个 job 的上限）。AutoFlow 只使用，不做本地限流、不校验 `timeout` 上限、不做密钥续期。

- 前提：AutoNote §12 先实施并部署，否则长运行或高并发的开发阶段会中途失败（429 或 401）。失败时 publish 照常保存已提交的进度、回帖 `paused`，回复「继续」会重新换取密钥接着做，不丢工作。
- 审查用手动访问密钥，上限仍是 8；审查每次只发一个请求，多个 PR 同时审查超出时按 `Retry-After` 重试。

## 6. 工作流

### 6.1 `agent.yml` 的 job

新增输入：`relay_url`（默认 `https://autonote.ouraihub.com`）、`architecture_path`（默认 `docs/概要设计.md`）、`standards_path`（默认 `docs/工程规范.md`）。删除输入 `doc_path` 和 secret `AI_KEYS`。`workflow_call` 增加输入 `issue`（数字字符串）。

| job        | 什么时候跑                                                      | 权限                                                | 做什么                                                                                                                                                                                                                                                         |
| ---------- | --------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dispatch` | `issues` / `issue_comment`，触发条件和现在 develop 的 `if` 相同 | `contents: read`、`issues: write`（加确认标签）     | 运行 `src/agent/dispatch.ts`：读 issue 评论，用 `nextStage` 算出加上这条评论前后的状态。之前 waiting、之后不 waiting，或者贴 `agent` 标签时还没有任何报告，才用 `AUTOFLOW_TOKEN` 执行 `gh workflow run <workflow> --ref <默认分支> -f issue=N`；否则什么都不做 |
| `develop`  | `workflow_dispatch`                                             | `contents: read`、`issues: read`、`id-token: write` | 现在的步骤，加 skills 安装；prepare 改为按阶段（§6.2）                                                                                                                                                                                                         |
| `publish`  | develop 之后，和现在一样总会运行                                | `contents: read`、`issues: write`                   | §6.3                                                                                                                                                                                                                                                           |

- `<workflow>` 是调用方工作流的文件名，从 `github.workflow_ref` 取（`owner/repo/.github/workflows/x.yml@ref` 中的 `x.yml`），不另设输入。`<默认分支>` 用 `github.event.repository.default_branch`；`workflow_dispatch` 事件里同样有这个字段。
- `concurrency` 改成按 `inputs.issue` 分组，dispatch 不进这个组。
- 派发之前（dispatch 和 publish 都一样），先用 `AUTOFLOW_TOKEN` 确认没有同一 issue 的 develop 在排队或运行：`gh run list -R <repo> --workflow <workflow> --status queued` 和 `--status in_progress`，按运行标题里的 issue 号过滤（`run-name: AutoFlow #${{ inputs.issue || github.event.issue.number }}`，模板里加这行）。publish 检查时排除自己所在的这次运行。已有就不派发，避免同一阶段跑两次。
- `await-*` 阶段不派发，也就没有 develop 运行。
- 模板 `templates/autoflow-agent.yml`：`on` 加 `workflow_dispatch: { inputs: { issue: { required: true, type: string } } }`，`permissions` 加 `actions: write`、`id-token: write`，`with` 里传 `issue: ${{ inputs.issue || github.event.issue.number }}`。

### 6.2 prepare

1. 读 issue（含评论作者和 `authorAssociation`），转成 `FlowEvent[]`，用 `nextStage` 算阶段。不是运行阶段，或者 waiting 为真（说明派发和状态不一致），写 `stage=` 空值退出，publish 回帖说明，不跑 omp。
2. 按 `roles.ts` 生成提示词，写进 `GITHUB_OUTPUT`：`stage`、`issue_dir`。
3. 换取访问密钥，写 `models.yml`（§5）。
4. 收集 `enabledSkills` 需要的事实，写 `skills.includeSkills`。skill 本身由 prepare 之前的一个 shell 步骤安装：对 02 §10 的三个仓库，各用 `git init` + `sparse-checkout set --no-cone <目录>` + `fetch --depth 1 --filter=blob:none` 拉取。ponytail 和 shadcn-svelte 取最新发布的 tag（`gh release view -R <repo> --json tagName`），hallmark 取默认分支。拉取的目录：ponytail 的 `/skills/`、`/hooks/`、`/pi-extension/`，hallmark 的 `/skills/hallmark/`，shadcn-svelte 的 `/skills/shadcn-svelte/`。`config.yml` 写 `extensions: [<ponytail>/pi-extension/index.js]` 和 `skills.customDirectories: [三个 skills 目录]`。这套步骤已在本地 Ubuntu、omp 18.12.6 上验证过（02 §10）。

### 6.3 publish

沿用现在的骨架：校验 bundle → 检查越界 → 快进推送 → 回帖。变化：

1. 越界检查用 `roles.ts` 的 `writes` / `readOnly`（§4.1）。
2. 算这次的 `outcome`。下面的规则按顺序判断，第一条成立就用它：
   - omp 没有正常退出：`paused`（有提交）或 `failed`（没有提交）；
   - `architecture`：分支相对默认分支的 merge-base，`<architecture>` 或 `<standards>` 有改动就是 `changed`，否则 `unchanged`；
   - `architecture-review`、`design-review`：`评审.md` 最后一节的 `对象` 和 `结论` 行（02 §17.2）。对象和阶段不符、缺行、值不认识，一律 `reject`；
   - `acceptance`：`测试报告.md` 最后一节的 `结论` 行，规则同上；
   - `develop`：任务没有全部勾选是 `paused`，全部勾选是 `done`；
   - 其他：`done`。
3. 回帖首行 `formatReport(stage, outcome)`，下面是给聊天看的摘要，内容按 02 §9。
4. 标签由 dispatch 加：在 `await-requirements` 收到确认时加 `agent:approved`，在 `await-design` 收到确认时加 `agent:design-approved`（第一次用时先 `gh label create`，和现在一样）。标签只给人看，`nextStage` 不读。`agent:develop` 不再使用。
5. 不是 `await-*`、不是 `review-pr`、不是 waiting，就用 `AUTOFLOW_TOKEN` 派发下一阶段。
6. `acceptance pass`：沿用现在开 PR 的代码。PR 正文链接 `需求.md` 和 `测试报告.md`，保留 `Closes #N`。
7. 换取访问密钥失败（§5 的 `config` 错误）时，prepare 在 `GITHUB_OUTPUT` 写 `relay_status`，publish 按 401 / 403 / 503 回帖，写明在 AutoNote 设置里该做什么。

### 6.4 审查

- `review.yml` secret 改为 `AUTONOTE_RELAY_KEY`，新增输入 `relay_url`、`standards_path`。
- `OpenAiCompatibleModel` 构造参数改为 `{ baseUrl, apiKey, model }`，只发一次请求；`NEXT_KEY_STATUS` 和 key 循环删除，对应测试改写为单个 key 的成功、HTTP 失败和响应缺内容。
- `PullRequestHost.rules()` 返回 `AGENTS.md` 和 `standards_path` 两份文件（都从 PR 的 base 读，缺失的写"无"）；审查提示词里两份都放进 Repository rules。
